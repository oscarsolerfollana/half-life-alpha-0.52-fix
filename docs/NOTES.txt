===============================================================================
 HALF-LIFE ALPHA 0.52 - SAVING AND LOADING GAMES
 Checked against enginegl.exe on 2026-09-18
===============================================================================

SUMMARY
-------
  SAVE     : DOES work (with "maxplayers 1").
  LOAD     : the alpha engine does NOT have it (sections 1 to 4), but it
             is written in full in hlsave.dll and works, also after
             reopening the game (sections 7, 8 and 13).


1. SAVING
---------
It works, but only in a single-player game. The engine checks the number
of players and if it is greater than one it answers:

    Can't save multiplayer games.

The alpha starts in multiplayer mode even if you pick "Single Player" (this
is described in the repack's own README.txt), so by default it never lets
you save. The fix is to force one player before loading the map:

    maxplayers 1
    map c1a1

The launcher "Half-Life Alpha Launcher.bat" already does this in options 1,
2 and 3.

Ways to save in game:
    F6                     quick save (creates valve\quick.sav)
    F2                     save menu (creates valve\s0.sav, s1.sav...)
    save <name>            from the console, ~ key (creates valve\<name>.sav)

The .sav files are written to the valve\ folder, NOT valve\SAVE\ (that
folder is empty and the engine does not use it).

Check done: with "maxplayers 1 / map c1a1 / save ztest" the engine
wrote a 66 KB valve\ztest.sav and the console showed
"Saving game to ...\valve\ztest.sav...". The save is correct and complete:
it contains the map name and, for the player, position (origin),
angles, health, weapon and ammo.


2. LOADING
----------
It does not work. On "load ztest" the engine answers:

    Loading game from ...\valve\ztest.sav...
    Savegame is version 4624156, not 16

And stays as it was. The number 4624156 is not a version: it is garbage,
a memory address inside the executable itself.

The cause, looking at the binary:

  a) The SAVE routine is the new Half-Life one. It writes a binary header
     "VALV" followed by version 16, and then the data. You can see it in
     the file: the first 8 bytes are 56 41 4C 56 10 00 00 00 = "VALV" + 16.
     That is, the .sav IS the version 16 the engine says it expects.

  b) The LOAD routine was never ported: it is still the Quake one, which
     expects a TEXT file and reads the version with fscanf(f, "%i\n", ...).
     Since the file starts with "VALV", fscanf finds no number, fails,
     and the version variable is left with garbage. Hence the 4624156.
     That is why the message is contradictory: it says it is not version
     16 when the file says exactly 16.

  c) And the underlying issue, which settles the matter: the game logic
     lives in valve\dlls\hl.dll, which exports DispatchSave and
     DispatchRestore. The engine resolves both pointers at startup, but
     ONLY ever calls DispatchSave. DispatchRestore is not called from
     anywhere in the executable: the pointer is stored, checked for null,
     and that is it. There is no entity restore path.

Conclusion: it is not a configuration problem, nor permissions, nor where
the .sav files are left. Loading is not implemented in this engine. Fixing
it is not a one-byte patch: the whole load routine would have to be written
(parse the VALV block, recreate the entities and call DispatchRestore
for each one) and injected into the executable.


3. WHAT CAN BE DONE IN THE MEANTIME
-----------------------------------
Option [2] of the launcher reads from each .sav which map it was saved on
and lets you start that map from the beginning. It does not restore
position, health or weapons, but at least it works as a "chapter select".

The .sav holds all the information needed to go further (exact position,
angles, health, weapon and ammo). With that a real checkpoint system could
be built, but the alpha engine has no command to teleport the player, so
the map's info_player_start would have to be rewritten. That is a separate
and much longer job.


4. FEASIBILITY OF WRITING THE LOADER (2026-09-18, corrected)
------------------------------------------------------------
WARNING: a first analysis in this section was wrong. When reading the
hl.dll export table I took the wrong column and disassembled functions that
were not the right ones. Done again properly, the result is the opposite of
what I first wrote.

Correct hl.dll exports (the FIRST objdump column is the index):
    GiveFnptrsToDll  0x1000dbf0   DispatchSave  0x10004020
    DispatchRestore  0x10004050

GiveFnptrsToDll copies a table of 64 engine pointers to 0x10032768. With
that, DispatchSave calls virtual method 3 of the entity and DispatchRestore
method 4. Searching all the vtables in the DLL, the 50-odd classes share
the SAME pair, never overriding it:

    Save    = 0x10001810
    Restore = 0x10001840

And here is the important part:

    Restore (0x10001840) is ONE SINGLE INSTRUCTION:  ret 0x4
    It is empty. It does absolutely nothing.

    Save (0x10001810) does not serialize either: it takes the classname and
    calls function 49 of the engine table with the string "Saving %s\n".
    It is a debug trace, not a save.

CORRECTED CONCLUSION: the game DLL saves and restores nothing. The
DLL-side save/restore is scaffolding Valve left in place and never
filled in. Everything in the .sav is written by the ENGINE: the entvars of
each entity as text (origin, angles, health, weapons, currentammo,
classname...) plus the globals and the lightstyles.

This has two sides:

  GOOD: there is no private format to reverse, and DispatchRestore is not
  needed at all. The work is 100% on the engine side, which is where it
  is comfortable to work.

  BAD: the fidelity ceiling is set by what is in the entvars. Player
  position, angles, health, weapons and ammo: yes. Internal state of
  monsters, half-open doors, timers: not saved, so there is no way to
  recover it. On load, the world would go back to its initial state and
  you appear where you saved, with your health and your weapons.


5. INJECTION PROBE: DONE AND WORKING (2026-09-18)
-------------------------------------------------
Command registration is at 0x42e8da onwards, with
Cmd_AddCommand = 0x426ab1:

    "load"  ->  handler 0x42d1bd   (the broken one)
    "save"  ->  handler 0x42cfc4

The "load" pointer is patched at file offset 0x2dce8 (it contained
bd d1 42 00 = 0x42d1bd).

There are 358 bytes of zero padding at the end of .text, at VA 0x45649a
(file offset 0x5589a), usable as a code cave.

TEST DONE: enginegl-carga.exe was created (patched copy, the original
enginegl.exe is not touched) with a 14-byte stub in the cave:

    push  <string>
    call  0x41754e        (the engine's Con_Printf)
    add   esp,4
    ret

and the "load" handler repointed to it. On running "load quick" the game
printed on its own console:

    [TEST] load hook active, load intercepted

That is: our own code can run inside the engine and use its functions.
The injection path is proven. The 358-byte cave is only enough for the
probe; for the real loader a section would have to be added to the PE.


6. CAN A COMPLETE SAVE AND LOAD BE DONE? (2026-09-18)
-----------------------------------------------------
YES, but NOT by touching only the load. The SAVE has to be extended too.

The reason is simple: the private state of the entities is not in the .sav
because it was never written (the DLL's Save is an empty trace). No
loader can recover data that is not in the file. The current .sav files
are unrecoverable by definition; a new format would be needed.

What makes this feasible is how entity memory is set up:

  - Entry 51 of the engine table (0x40a013) = PvAllocEntPrivateData:
        free_previous(edict)
        if (size > 0) pointer = calloc(1, size)
        edict[0x74] = pointer
    The size is passed by the DLL, and the block is allocated by THE ENGINE.

  - Entry 52 (0x40a03d) = returns edict[0x74]
  - Entry 53 (0x40a045) = frees it

  - There are 117 call sites in hl.dll, one per class, each with its
    size (e.g.: push $0x1c = 28 bytes) and writing its vtable at
    offset 0 of the freshly allocated block.

That is: the private state of each entity is ONE FLAT heap BLOCK, of
known size, and everything goes through ONE SINGLE engine function. That
is the choke point that is needed.

PLAN FOR A COMPLETE SAVE:
  1. Patch entry 51 to record the size of each block (the engine
     does not keep it today; it has to be noted in a side table per edict).
  2. On save, also dump the raw block of each entity.
  3. Pointer "swizzling" pass: walk each block 4 bytes at a time
     and, if a value falls inside another entity block or the edict
     array, replace it with a symbolic token (index + offset). On
     load it is resolved again. This avoids having to understand the
     internal layout of the 117 classes, which would be unfeasible.
  4. On load: allocate, memcpy the block, and fix up pointers.
     The vtable (offset 0) restores itself because the DLL loads at fixed
     base 0x10000000. The pev pointer (offset 4) is recomputed.
     >>> NOTE: the fixed base thing is FALSE, and it caused the failure in
     section 13. hl.dll is relocated on every start. The vtable must be
     rebuilt. <<<

MAIN RISK: swizzling is the gamble. False positives (an integer
that matches an address) are unlikely but possible, and
pointers to things in the engine hunk need their own handling.
There is no known wall, but no guarantee either until tested.


7. WORK IN PROGRESS: COMPLETE SAVE (2026-09-18)
-----------------------------------------------
SETUP
  src-carga\motor.h      engine addresses and structures
  src-carga\hlsave.c     the logic
  src-carga\compilar.sh  builds with the w64devkit i686 mingw
  src-carga\parchear.ps1 regenerates enginegl-carga.exe from the original
  hlsave.dll             build output
  enginegl-carga.exe     patched engine (enginegl.exe is NOT touched)

Injection is via the entry point: parchear.ps1 puts a 16-byte stub
in the .text cave (0x45649a) that does LoadLibraryA("hlsave.dll")
and jumps to the original startup (0x444660). All the rest of the patching
is done by the DLL in memory when it loads, so iterating is just
rebuilding the DLL.

1997 BUG FOUND AND FIXED
  The original save allocates a FIXED 64 KB buffer (push 0x10000 at
  0x42d036) and puts the whole state inside it. Any real map overflows it:
  the four factory .sav files weigh between 66,026 and 66,987 bytes, and
  the c1a1 one comes out at 66,056. It always overflowed, corrupted the
  heap and the game crashed when freeing the buffer, AFTER having written
  the file. That is why the "done." message never appeared and it looked
  like it hung.
  Fixed by enlarging the buffer to 1 MB (in-memory patch of the operand at
  0x42d037). Now "done." appears and the save finishes cleanly.

  That is: saving in the alpha was not just incomplete, it also brought
  the game down every time. That no longer happens.

EXTENDED SAVE (working)
  Entry 51 of the engine table (the private data allocator) is hooked
  to record the block size of each entity, which the engine
  receives but does not keep. And the "save" handler is repointed so that,
  after the original save, it appends to the file:

      "CLDX" | version | num_edicts
      per edict: size | raw block | nrelocs | relocs[]
      reloc = { offset, kind, target, inside }
      kind 1 = pointer to an edict,  kind 2 = pointer to another block

  The relocation list is built by walking each block 4 bytes at a time
  and checking whether the value falls inside the edict array or another
  private block. This way the internal layout of the classes need not be
  understood.

  TESTED on c1a1: 157 edicts, 153 with private state, 153 pointers
  recorded, file from 66,056 -> 95,060 bytes, no crash. The typical
  relocation is the pev pointer at offset 4 of the block, pointing to
  edict+0x78. Matches what was expected.

PENDING: loading.
  It must be written from scratch (the original is Quake's text parser and
  is no good). Steps: read the file, start the map without the BSP spawning
  the entities, recreate the edicts with their entvars using ED_FindField
  (0x408996) and ED_ParseEpair (0x40947b), restore the private blocks and
  apply the relocations.


8. LOADING, WORKING (2026-09-18)
--------------------------------
Written in full and tested. The chain is:

  "load name"    ->  mi_load: reads the file, gets the map name,
                     marks a pending load and queues "map <map>" AT THE
                     FRONT of the queue (Cbuf_InsertText, 0x42643e;
                     with Cbuf_AddText it would go after the rest of the
                     script).
  "map"          ->  hooked at 0x42e76e. Starts the map as always
                     and, if there is a pending load, restores the state.

A custom command cannot be registered for the second step:
Cmd_AddCommand (0x426ab1) checks host_initialized (0x8572a4) and aborts
the game with "Cmd_AddCommand after host_initialized". Hence the
"map" command itself is hooked.

TWO TRAPS THAT TOOK A WHILE
  a) The file was opened with FILE_APPEND_DATA. With that flag EVERY
     write goes to the end no matter what, so seeking back to
     fill in the string count appended instead of overwriting and
     threw the whole file out of alignment. It must be opened with
     GENERIC_WRITE.
  b) When restoring an edict its header can NOT be zeroed. Bytes
     0x04..0x77 hold the area links, a doubly linked list
     between edicts. If they are zeroed without unlinking first, the
     neighbours keep pointing to a dead node and the engine blows up
     when walking the list.
     Fix: only touch the entvars (0x78 onwards) and the free flag.

  Also, the restore validates the whole block BEFORE touching anything;
  otherwise a corrupt file would leave the game half destroyed.

CONCLUSIVE TEST (c1a1, save after 13.6 s of play and then load):

  ON SAVE                t=13666ms vida=100 origen=(-28 1260 -299) suma=0x7ba3bba7
  MAP JUST STARTED       t= 1200ms vida=  0 origen=(  0    0    0) suma=0x00000000
  AFTER LOAD             t=13666ms vida=100 origen=(-28 1260 -299) suma=0x7ba3bba7

  The middle line is the key: the freshly started map has a COMPLETELY
  different state (clock at 1.2 s, health 0, origin at the center of the
  world and the private block all zeros). After restoring, everything is
  exactly what was saved again, including the checksum of the 452 bytes
  of the player's private C++ block. So the private state travels
  whole, which was exactly what the alpha did not do.

  157 edicts, 153 with private state, 153 relocations applied,
  0 used/free mismatches.

STILL TO TEST / POLISH
  - Save and load have only been tested within the same session and on the
    same map. Loading right after starting the game is still to be tested.
  - The process does not fully exit with "quit" after a load; it
    hangs on close. It does not affect the game but must be looked at.
  - The warning "maxplayers can not be changed while a server is
    running" appears because the queued command carries maxplayers 1.
    It is cosmetic.
  - The case where the map starts with a number of entities different
    from the saved one is still to be checked (there SV_LinkEdict and
    SV_UnlinkEdict would be needed, not located yet).
  - Lightstyles and progs globals are not restored.


9. COLD LOAD AND LAUNCHER (2026-09-18)
--------------------------------------
COLD LOAD (loading right after starting the game): STILL CRASHES.

  It turned out that restoring right after "map" does not work cold: the
  client takes several frames to connect, so the player does not exist
  yet (visible in the trace: priv=0 on restore). The hook was moved to
  the "begin" command (0x42e1d7, operand at 0x42e8a0), which closes the
  client handshake. Now the state IS restored properly cold too, but the
  game blows up after the restore finishes. The failure is in what the
  engine does after "begin", not inside the restore ("restaurar: hecho"
  always appears before the shutdown.)

  Hypothesis to check: after "begin" the engine sends the client the
  baselines of all entities, and something restored does not fit.

THE HOOK ON "begin" IMPROVED THE HOT TEST
  Now the trace shows three clearly different states:
      ON SAVE            t=11431ms suma=0x0f61b5e4
      CLIENT IN GAME     t= 1415ms suma=0x50611684   <- player just

      AFTER LOAD         t=11431ms suma=0x0f61b5e4

10. VIEW ANGLES ON LOAD (2026-09-18)
------------------------------------
SYMPTOM (seen while playing, not in the logs): on load, the game comes back
fine but the player always looks in the same direction.

CAUSE: the angles ARE restored on the server, they are in the entvars and
are copied raw like everything else. But the CLIENT keeps its own copy of
where it is looking and does not notice the server has changed it.

FIX: set fixangle=1 on the player entity after restoring. The
server then sends an svc_setangle and the client jumps to that
direction. NOTE: svc_setangle sends v.angles, NOT v_angle. They are
different fields and for players they do not hold the same value (Quake
stores in angles the pitch divided by 3, because it is for the model others
see, not for your view). That is why angles is set to v_angle before raising
the flag. It is in forzar_vista_jugador().

All three fields exist in the alpha (v_angle, angles, fixangle) and the
function runs, as the log shows:
    vista: v_angle=(0 0 0) copiado a angles, fixangle puesto

NOT VALIDATED YET: the automated tests do not move the mouse, so
v_angle always comes out (0 0 0) and they prove nothing. It has to be
checked by playing: look at an odd spot, save, turn around, load.

Reminder: no automated test caught this bug. From the log the angles
looked correct, because they were: the one that was wrong was the client.


11. ROLL STUCK ON LOAD (2026-09-18)
-----------------------------------
SYMPTOM (seen while playing): if you save while strafing and then
load, you stay tilted. And it does not straighten out by itself.

CAUSE: the fix in section 10 copied ALL THREE angles from v_angle to
angles, roll included. But roll is not a real view angle: it is the tilt
effect when strafing, which the engine recomputes by itself every frame
from the velocity. Forcing it on the client with svc_setangle leaves it
stuck in cl.viewangles, and since the mouse only touches pitch and yaw,
nobody ever sets it back to zero.

FIX: when forcing the view, angles[2] (the roll) is set to zero on
purpose. Pitch and yaw are restored. It is in forzar_vista_jugador().

Lesson for what is left: not everything in the entvars should be
restored. Some fields are derived state, recomputed by the engine, and
restoring them does more harm than good. Watch out for the other view
effects (punch angles and the like) if similar symptoms appear.


12. THE HUD IS NOT VISIBLE: IT IS "sizedown" (2026-09-18, SOLVED 2026-09-20)
----------------------------------------------------------------------------
SUMMARY: the HUD starts switched off and the command that turns it on is
"sizedown". It is not the resolution, not the patch and not the art.

Clue that uncovered it: with "Half-Life GL Launcher.bat" the HUD IS visible.
That .bat launches with exactly the same video (-width 800 -bpp 32) as
the new launcher, so the resolution was ruled out from the start.

THE TWO COMMANDS, TAKEN APART
  sizeup    -> 0x42b427 -> 0x404541
      if viewsize < 120: viewsize += 10  (Cvar_SetValue "viewsize")
      if already at 120: DECREMENTS the HUD level (clamp at 0)
  sizedown  -> 0x42b437 -> 0x404588
      INCREMENTS the HUD level; past 3 it pins it at 3 and
      starts lowering viewsize -= 10
  (names at 0x467f14 and 0x467f1c; the wrapper also sets
   0xd3b434 = 1, the flag to recompute the refdef)

  That is why trying "sizeup" showed nothing: it goes the other way.

  The only FOUR writes to 0x45a808 in the whole .text are the
  clamp at 0 of sizeup and the clamp at 3 of sizedown. Nothing else touches
  it: not map start, not load, not level change. And it is NOT
  saved in config.cfg (it is not a cvar), so every start begins
  at 0 and it has to be requested again.

WHAT EACH LEVEL DRAWS (screenshots in valve\quake02..05.tga, c1a1, 800x600)
  0 : nothing
  1 : health bar at the bottom left
  2 : + the frame/column on the right
  3 : + the panel at the top left
  4th sizedown : same as 3 (the clamp kicks in; the viewsize -= 10 is not
      noticeable in the GL render)

  And the 640 art FITS at 800x600: the pieces are anchored to the
  corners, not scaled. The suspicion that it would only work at 640 was
  unfounded.

CHECKED WITH BOTH ENGINES
  enginegl.exe (original) and enginegl-carga.exe (patched), same
  command line as launcher option [1]:
    -heapsize 524288 -condebug -width 800 -bpp 32 +maxplayers 1
    +map c1a1 +sizedown +exec cap_a.cfg
  Both show the HUD. Also confirmed that "+sizedown" after
  "+map" IS executed: it does not need to be moved earlier in the command
  line.

  The original section said "identical screenshots with both engines,
  and none with HUD". It was true, but proved nothing: that capture
  cfg had no sizedown, so both runs were at
  level 0.

HOW THE SCREENSHOTS ARE TAKEN (still valid)
  - cfg with: waits, whatever command, waits, screenshot, waits, quit
    (one "wait" is one frame; 120-150 is plenty)
  - launch with +exec <cfg>; FROM POWERSHELL with Start-Process, not
    from the bash shell: from bash the engine dies right after
    writing "Console initialized." and exits with code 1
  - the screenshot lands in valve\quakeNN.tga, NOT in valve\glquake\
  - convert with: ffmpeg -i input.tga -vf vflip output.png
    (the vflip is needed: the TGA goes bottom to top)
  - valve\hud_niveles.cfg is left in place, which goes through the four

DECIDED (2026-09-20): the launcher keeps ONE single "sizedown", that
is level 1: only the health bar. That is already what it sends in the four
options, nothing to change. If the full HUD is ever wanted,
it is three "sizedown".

13. LOADING AFTER REOPENING THE GAME: FIXED (2026-09-22)
--------------------------------------------------------
SYMPTOM: you save, close the game, open it again, load and it crashes.
Within the same session it worked, and that was exactly what was misleading.

THE CAUSE, IN ONE LINE: the .sav carried memory addresses of the
process that saved. In the same session they work by miracle (the process
is the same or lands on the same addresses); in a new process they are dead
pointers.

Analyzing an old .sav (valve\quick.sav) outside the game,
the raw pointers were of three kinds:

  286  pointers into hl.dll  -- the C++ vtable at offset 0 of each
       private block, plus method pointers. THIS WAS THE BULK OF IT.
  156  pointers into the edict array IN THE ENTVARS (offset 0x208, the
       pContainingEntity: each entity points to its own edict). The
       entvars were not scanned at all, only the private blocks.
  308  pointers to an engine structure in the hunk (0xa2a1168 in that
       run, the same for all entities), 156 in the entvars and
       152 in the private blocks.

THE ORIGINAL MISTAKE WAS IN SECTION 6 OF THESE NOTES
  It said: "the vtable (offset 0) restores itself because the DLL loads at
  fixed base 0x10000000". It is FALSE. hl.dll has a relocation table
  (.reloc, 0x3b5e bytes) and Windows places it wherever it likes. Bases seen
  in four starts in a row:

      0x1f160000   0x3daf0000   0x3d5f0000   0x3d5c0000

  So it changes on EVERY start, not only on reboot. Checked without a
  debugger: the dword at offset 0 of the world's private block was
  0x1f18c1d8 in the old .sav, and with base 0x1f160000 that is rva
  0x2c1d8, which in hl.dll falls in .rdata and has the common Save
  (0x10001810) in slot +0xc. It is a vtable, and that run's base was in it.

FIX (CLDX format version 3)
  1. THE ENTVARS are scanned too, not only the private blocks.
  2. Two new relocation kinds:
       kind 3 (hl.dll): the offset inside the module is stored and on load
                it is rebuilt on whatever base hl.dll has NOW.
       kind 4 (live):   pointers into the engine hunk that we cannot
                name. They cannot be recomputed, so on load the value
                of the FRESHLY STARTED map is kept, which does point to
                this session's structures. For that the restore takes a
                copy of the private blocks BEFORE destroying them.
  3. The header stores that session's hl.dll base, only for the
     trace: the log shows "al guardar=... ahora=... (MOVIDA)".
  4. Pointers to static data of the .exe are left as they are: the
     executable has no relocations and always loads at 0x400000. That is
     where the strings live, which also already travelled as text.

  How to recognize a hunk pointer without confusing it with a float: it is
  only accepted if it falls in a 1 MB window around the edict array and if
  VirtualQuery says there is committed memory. The ones seen fall less than
  2 KB from the array, and the narrow window leaves out the range of the
  normal floats of a map (coordinates, times).

  Version 2 .sav files no longer load: they lack the information to
  relocate anything. The game says so and they have to be redone.

THE TEST (c1a1, two different processes, 2026-09-22)
  Process 1:  +map c1a1, wait, "save zfria", "quit"          -> exit 0
  Process 2:  "load zfria", wait, "screenshot", "quit"       -> exit 0

      ON SAVE                t=4697ms vida=100 org=(-28 1260 -299)
      MAP JUST STARTED       t=1200ms vida=  0 org=(  0    0    0) priv=0
      CLIENT IN GAME         t=1413ms vida=100 org=(-28 1260 -271)
      AFTER LOAD             t=4697ms vida=100 org=(-28 1260 -299)

      restaurar: hl.dll al guardar=0x3d5f0000, ahora=0x3d5c0000 (MOVIDA)
      restaurar: punteros rehechos: edict=310 privado=0 hl.dll=260 vivo=310
                 (sin copia=0 descartados=0)
      restaurar: contenido de los bloques privados: 153 comparados, 0 distintos

  The content line is the one that matters now. The checksum from
  before no longer works for cold loading: the pointers are legitimately
  different, so the checksum HAS to change. What is compared is the
  block in the file against the one in memory ZEROING the dwords that carry
  a relocation: everything that is not a pointer comes out byte-for-byte
  equal in the 153 blocks, and the pointers come out recomputed. That does
  discriminate.

  Also, the game stayed alive hundreds of frames after restoring
  (it wrote the screenshot valve\quake00.tga: map drawn, HUD with health
  at 100 and the scientist animating, so the vtables work) and
  exited cleanly with "quit", which did not happen before either.

14. CRASH WHEN DRAWING DECALS: FIXED (2026-09-23)
-------------------------------------------------
SUMMARY: a 1997 engine bug, not a hlsave.dll one. With more than 500
surfaces with decals (bullet holes, blood, scorch marks) in
view, the engine wrote past a fixed list and ended up crashing.

THE CRASH
  2026-09-23 20:03:39, c0000005 at enginegl-carga.exe+0x3881d
  (0x43881d, mov ecx,[eax] in the loop that draws the decals, with
  glPolygonOffset). Nothing was saved or loaded in that game:
  hlsave.log only has the startup.

THE BUG
  List of surfaces with a decal: 500 pointers at 0x819bb8, counter at
  0x819bb0 (reset to 0 every frame at 0x43752c and after drawing at
  0x438a41). The routine that adds (0x436b91) increments the counter,
  WRITES the entry and only afterwards compares with 500; when over it prints
  "Too many decal surfaces!" (0x46a170) via Con_Printf (0x40a559, not

  mov eax,[0x819bb0] / cmp eax,500 / jge 0x436bb7 /
  mov [eax*4+0x819bb8],esi / inc eax / mov [0x819bb0],eax / 13 nops
  Fills the list, the surplus surface is not drawn that frame. The
  warning was removed: with the jump back it did not fit in the 38 bytes.
  The script checks the original bytes before patching.


15. THE CROSSHAIR WAS NOT ON THE AIM POINT: FIXED (2026-09-23)
--------------------------------------------------------------
SYMPTOM: shots (tested with the pistol) land a little
above the crosshair. It is not the weapon: it is the crosshair that is
misplaced, so it affects all of them.

THE CAUSE
  The engine draws everything on a 320x200 virtual screen (vid at
  0xd3b424/0xd3b428 = 320,200; R_SetupGL at 0x421f28 has the 320 and the
  200 hardcoded) which is stretched to the real resolution. The 3D view
  takes the whole screen (vrect 0x0c67660 = 0,0,320,200; sb_lines 0), so
  it aims at the exact center: (400,300) at 800x600.
  The crosshair (cvar "crosshair", struct at 0x46b638) is drawn with
  Draw_Character(vrect.x + w/2, vrect.y + h/2, '+'): the CORNER of the
  cell at the center, and the conchars '+' sits in the lower part of its
  cell. Stretched x2.5 / x3, the drawing ended up at (406, 319.5): 20 px
  below and 6 to the right of the real aim point.

THE FIX (parchear.ps1, static, at 0x42bcf7 and 0x43d982)
  The two places that draw the crosshair do cdq/sub eax,edx/sar eax,1
  to divide by 2; since w and h are positive the cdq/sub does
  nothing, and in its room 14 is subtracted from h and 6 from w: center -7
  and -3 in virtual units. Measured on a screenshot at 800x600: horizontal
  arm on row 299, vertical 1 px left of the center. Being in
  virtual units it holds for any resolution.


16. SHOTS DEVIATED DEPENDING ON WHERE YOU LOOK: FIXED (2026-09-23)
------------------------------------------------------------------
SYMPTOM (seen while playing, after centering the crosshair in section 15):
looking up the shot goes below the crosshair, looking down above it,
straight ahead it is fine. And always a little to the right.

CAUSE 1, THE BIG ONE: THE ANGLES TRAVEL TRUNCATED
  CL_SendMove (0x40be7f) sends cl.viewangles (0x8493d8) with
  MSG_WriteAngle (0x42ef75) = ((int)f * 256 / 360) & 255, the Quake one:
  one byte (steps of 1.40625 degrees) and TRUNCATING twice. The server
  fires with that v_angle. Yaw is always in 0..360, so
  truncating lowers it = turns right (up to 1.4 degrees). Pitch
  truncates toward 0 = toward the horizon: looking down (positive) the shot
  goes up, looking up it goes down. Exactly the symptom.
  Fix (parchear.ps1): 0x42ef75 jumps to the cave 0x4564c0, which does
  trunc(f*256/360 + 256.5) (the +256 keeps it positive so that truncating
  is rounding); MSG_WriteByte (0x42ee95) only stores the low byte.
  Measured in game: client 49.130 -> server 49.219 (before 47.8);
  client (-1.056 359.072) -> server (-1.406 358.594).

CAUSE 2, SMALL: THE BULLET DID NOT COME OUT OF THE EYE
  hl.dll's FireBullets (0x100103f0) used as origin
  origin + v_forward*10 in x,y and origin.z + view_ofs.z - 4 in z. It is a
  parallel offset of a few units that also changes with
  pitch. Fix in hl.dll (regenerated by parchear.ps1 from
  hl-original.dll, an untouched copy of the factory one): the three fld of
  v_forward become fldz and the fsub 4.0 becomes fcom 4.0. Only
  opcodes are touched: hl.dll is relocated on every start and the address
  operands carry a relocation entry.

RULED OUT
  - The pistol aims with v_angle (entvars +0x160), not with angles (which
    carries the pitch /3 for the model). Real offsets, read from the
    live field table: angles 0x4c, punchangle 0x70, view_ofs
    0x148, fixangle 0x15c, v_angle 0x160.
  - The direction comes from aim() (function 30 of the engine table,
    0x40367c), Quake's autoaim, but sv_aim is "1" by default
    and with that it deviates nothing.
  - The spread's RANDOM_FLOAT is symmetric.

WATCH OUT WITH THE AUTOMATED TESTS
  - The cfg must use LF: with CRLF (PowerShell's Set-Content)
    the commands are not recognized.
  - At most ~8 KB of cfg: otherwise "Cbuf_AddText: overflow" and nothing
    runs. 2000 waits no longer fit.
  - With +lookdown/+lookup in the cfg the view does move (useful to
    test pitch without a mouse).

EXTENSION (same day): CLC_MOVE ANGLES IN 16 BITS
  While playing it was still off-center ("now it always shoots high").
  Measured: the camera (r_refdef.vieworg 0xc676d0, viewangles 0xc676dc) is
  at the server's eye (origin + view_ofs) within 0.1 units, standing and
  walking, and its angles are those of cl.viewangles. The only thing left
  was the byte: even rounding, steps of 1.4 degrees = up to 0.7 of error
  (client 18.774 -> server 18.281: half a degree higher).
  Fix, as Half-Life did later: clc_move carries the angles in
  16 bits. CL_SendMove (call at 0x40bed6) -> WriteAngle16 at 0x4564f0
  (round(f*65536/360), MSG_WriteShort 0x42eeaa); SV_ReadClientMove
  (call at 0x418518) -> ReadAngle16 at 0x456530 (MSG_ReadShort 0x42f00d
  * 360/65536). The rest of the messages still use one-byte
  MSG_WriteAngle/ReadAngle (rounding). Measured: 18.7679 -> 18.7701;
  244.2371 -> -115.7629 (= 244.2371). The server already received
  -180..180 with the signed byte, so for hl.dll the format does not change.
  The bullet holes in tests straight at a wall: within 10 px
  of the center and in different directions, that is the pistol spread
  (vector 0.01 = about +-4 px at 800x600).

says "SZ_GetSpace: overflow". That frame's effects are lost.

pushes the player sideways.

0x439c03) it jumps to a cave (0x456560) that sets cl.viewangles[ROLL]
to 0 and returns to 0x439a76. The view roll when walking is added by
the drawing separately and does not go through there. It holds for any
fixangle, not only for loading.
